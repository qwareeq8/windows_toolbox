# Virelo Verification and Audit, 2026-07-16

## Outcome

The source, frontend, Windows integrations, registry recovery design, and release tooling were
audited and materially hardened. Live checks confirmed the two reported fixed-size application
cases, Google Drive and LightBulb, are centered without resizing and restore exactly. A live File
Explorer Details tab fitted all four visible columns. No executed check remained failed at the
audit checkpoint.

This is not a blanket certification. The destructive Details-default operation was deliberately
not applied to the author's real Explorer profile, and the complete install, upgrade, recovery,
and uninstall matrix requires a disposable Windows acceptance machine. Clean packaging and
artifact identity are post-commit gates: their results must be reported in the final handoff and
retained checksum records because embedding those hashes here would change the source commit from
which the artifacts were built. Those boundaries are listed under
[Verification status](#verification-status).

## Findings and corrections

### Window centering and restore

The baseline detected fixed-size targets but still forced them to a replacement size. That behavior
is wrong for applications such as Google Drive and LightBulb, whose custom frameworks expose
windows that do not resize cleanly.

The audited implementation now:

- Uses `WS_SIZEBOX` to classify a foreground window as resizable.
- Centers the DWM-visible frame instead of the raw Win32 rectangle.
- Preserves the exact width and height for fixed-size windows.
- Retains raw-rectangle and invisible-border deltas so restore is exact even when the DWM frame
  differs from `GetWindowRect`.
- Clamps restored visible geometry to a monitor work area without incorrectly forcing invisible
  borders inside that area.
- Rejects Virelo's own window, the shell, unsuitable full-screen targets, and invalid windows.
- Rolls back safely if a replacement keyboard hook cannot be installed and uses monotonic time for
  shortcut state.

Live native results on the audit machine were:

| Application  | Classification             | Original raw rectangle | Centered raw rectangle                       | Center error   | Restore |
| ------------ | -------------------------- | ---------------------- | -------------------------------------------- | -------------- | ------- |
| LightBulb    | Fixed-size Avalonia window | `(1045,521,1515,871)`  | Same 470 by 350 size                         | `(0,0)` pixels | Exact   |
| Google Drive | Fixed-size ATL window      | `(1273,660,2313,1399)` | `(760,330,1800,1069)`, same 1040 by 739 size | `(0,0)` pixels | Exact   |

Neither case used a resize fallback. Geometry unit tests also cover resizable windows, fixed-size
windows, invisible borders, off-screen restoration, and negative-coordinate arithmetic. Physical
multi-monitor acceptance with mixed scale factors and negative monitor coordinates remains a
manual release gate.

### Explorer column auto-fit

The baseline could conflate tabs that showed the same path, key state too heavily by path, retry a
noninteractive tab too aggressively, and treat a partial fit as success. Those behaviors could
miss navigation transitions and waste CPU.

The audited implementation now:

- Tracks each tab by stable COM `IUnknown` identity plus its native tab identifier, so same-path
  tabs remain distinct and an `A -> B -> A` navigation re-arms work.
- Re-arms when a tab enters Details view, suppresses retries in other view modes, targets the exact
  tab identity, and invalidates disconnected Explorer COM proxies.
- Uses `IColumnManager` to enumerate the currently visible columns and applies the fit width to
  each one. Any failed column makes the operation fail and retry instead of reporting partial
  success. This follows Microsoft's documented
  [`IColumnManager`](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nn-shobjidl_core-icolumnmanager),
  [`GetColumns`](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-icolumnmanager-getcolumns),
  and [`SetColumnInfo`](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-icolumnmanager-setcolumninfo)
  interfaces.
- Canonicalizes UNC paths without damaging the server and share prefix.
- Waits through `MsgWaitForMultipleObjects`, pumps the STA COM message queue, and backs off from
  150 milliseconds after activity to one second when idle.

The baseline retry clamp allowed an overdue pending retry every 5 milliseconds, or as many as 200
cross-process enumeration attempts per second. The audited clamp is 50 to 500 milliseconds and
honors the 500-millisecond noninteractive retry deadline. This is a code-path comparison, not a
before-and-after CPU benchmark.

The live post-fix measurements were:

- One open Explorer Details tab: 4 of 4 visible columns fitted through COM in 87.76 milliseconds.
- Warm worker sample: 5.006 seconds wall time, 0.0312 CPU seconds, or 0.624 percent of one logical
  core; the worker stopped cleanly.

Native identity integration tests exercised real pywin32 and comtypes `IUnknown` behavior. Unit
tests separately cover same-path tabs, navigation re-entry, Details transitions, retry deadlines,
partial failures, idle backoff, proxy invalidation, and UNC canonicalization.

### Explorer Details defaults and recovery

Virelo now offers one opinionated Details-default action rather than reproducing WinSetView's full
option surface. The design intentionally follows the Explorer model documented by the
[WinSetView manual](https://lesferch.github.io/WinSetView/Manual.html): clear saved per-folder
views, create current-user folder-type defaults, and let Explorer use those defaults the next time
a folder opens. WinSetView's
[What to Expect](https://github.com/LesFerch/WinSetView/blob/main/WhatToExpect.md) correctly warns
that clearing saved views removes individual folder customizations. Virelo surfaces that boundary
before applying the change.

The implementation:

1. Takes an exact structured snapshot of all six affected HKCU keys before mutation, including
   whether each key originally existed.
2. Uses a schema version, SHA-256 digest, pending marker, 128 MiB size limit, depth limit, fixed
   key allowlist, and supported registry-type encoding. Ambiguous legacy `.reg` backups fail
   closed.
3. Clears the two Bags and BagMRU locations plus `Streams\Defaults`, copies the machine
   `FolderTypes` tree to HKCU, sets every `TopViews` entry to Details, and writes the special
   This PC bag values.
4. Verifies writes and restores the original snapshot automatically if apply or reset fails.
5. Creates a second safety backup before a user-requested restore.

The live test against the author's real HKCU profile was read-only: all 6 entries were captured,
5 existed, the manifest was 27,091,327 bytes, and digest validation and temporary cleanup passed.
A separate isolated native HKCU subtree test round-tripped string, binary, multi-string, and QWORD
data and exercised copy and deletion. Unit tests cover absent keys, malformed or oversized
manifests, digest mismatch, unsupported content, rollback, and restore ordering.

The real apply, reset, and restore actions were not run against the author's active Explorer
profile. They intentionally clear current layouts and could interfere with live file operations.
Virelo also does not kill or restart Explorer automatically. The user must finish copy, move,
rename, and delete operations, then restart File Explorer or sign out after the registry action.

### Settings, lifecycle, and interface

- Settings now validate unknown keys, types, ranges, choices, and hotkey combinations before
  mutation. Draft application is transactional and restores both runtime and persisted state when
  a side effect fails.
- Startup-shortcut mutations preserve the exact prior link bytes, failures roll back before
  settings persist, stale or unreadable links can be replaced safely, and the tray state reflects
  the shortcut that actually launches the current build.
- Quit offers save, discard, and cancel behavior for unsaved changes. Worker ownership and shutdown
  now wait for terminal states instead of abandoning background registry work.

### Embedded frontend security

Release mode now fails closed if the packaged frontend is missing and does not silently enable a
mock bridge. It allows local resources only from the packaged frontend root, the exact Qt
WebChannel resource, and the one trusted internal error document. Remote resource requests,
arbitrary local-file navigation, dropped navigation, and ordinary data-URL navigation are
blocked. Development access requires explicit `VIRELO_DEV=1` and matches the exact
`http://localhost:5173` origin.

This design uses Qt's documented
[`QWebEngineSettings`](https://doc.qt.io/qt-6/qwebenginesettings.html) controls and a
[`QWebEngineUrlRequestInterceptor`](https://doc.qt.io/Qt-6/qwebengineurlrequestinterceptor.html).
The interceptor performs only constant-time URL checks because Qt notes that request handling
stalls the request while the interceptor runs. Security-focused unit tests cover release and
development URL decisions, WebChannel scope, and trusted error navigation. This was not an
independent penetration test.

### Build and installer practices

- Python 3.12 to 3.14 and x64 are explicit. A constrained Python build environment and npm lockfile
  make resolved tool and application versions reproducible within those files.
- The build records source commit, clean/dirty state, platform, input hashes, frontend hashes, PE
  versions, hidden files, and a complete one-folder checksum inventory. Packaged smoke testing is
  a blocking gate, and a failed Git status query stops the build instead of producing false clean
  provenance.
- The distributed bundle now includes the repository's MIT license. Third-party notice and
  license obligations for the redistributed runtime remain a separate public-release review gate.
- CI covers Python 3.12 to 3.14, frontend checks, packaging, and installer construction.
- Inno Setup now requires x64 Windows 10 build 17763 or later, removes stale bundle payload before
  upgrade, and checks both local and global application mutex names. Its behavior follows the
  official [`AppMutex`](https://jrsoftware.org/ishelp/topic_setup_appmutex.htm),
  [`PrivilegesRequired`](https://jrsoftware.org/ishelp/topic_setup_privilegesrequired.htm),
  [`Run` section](https://jrsoftware.org/ishelp/topic_runsection.htm), and
  [constants](https://jrsoftware.org/ishelp/topic_consts.htm) documentation. In particular,
  `PrivilegesRequired=admin` means alternate UAC credentials change the account under which setup
  runs, and user-profile constants must not be assumed to identify the interactive account.
- Signature-required verification fails closed. This audit machine has no approved signing
  identity, so any locally generated candidate is expected to report `NotSigned` and must not be
  described as a signed public release.

## Final acceptance rule

The application is source-audit complete but is not release-accepted until every pending artifact
gate passes and the environment-limited lifecycle rows are either executed successfully or
explicitly accepted as release risks. Preserve the original bundle, the final build log,
`.release.json`, both checksum inventories, signature output, UI evidence, and this report together.
